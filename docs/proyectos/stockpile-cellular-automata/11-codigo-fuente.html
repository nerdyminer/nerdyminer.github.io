Leer el sistema en el orden de sus decisiones

Como hemos aprendido en nuestro apunte dedicado a la teoría de grafos, un DAG es un grafo dirigido sin ciclos. En un proyecto de datos, cada nodo representa una pieza que puede producirse o verificarse y cada flecha indica que una pieza depende de otra. El DAG de Dagster nos permitió observar el linaje general del proyecto, desde la lectura de datos hasta la simulación y sus chequeos. Sin embargo, un grafo de dependencias no explica qué sucede dentro de cada nodo. No muestra por qué la grilla debe tener un centro único, cómo se conserva el volumen durante una descarga ni en qué momento una columna de caudal se transforma en material dentro del autómata.

Este último capítulo cambia entonces la escala de observación. Ya no preguntaremos solamente qué depende de qué, sino también dónde vive cada decisión y cómo podemos seguirla en el código. Un repositorio, la carpeta versionada que reúne el programa, su configuración, sus pruebas y su documentación, no debería leerse de manera alfabética. Hacerlo así equivale a estudiar una planta recorriendo sus equipos por número de placa. Es preferible seguir el proceso: Primero se declara el mundo posible, después se validan las entradas, luego se ejecuta la física y, finalmente, se publican los resultados.

El explorador que aparece a continuación presenta los archivos en ese orden pedagógico. Es una aplicación estática incluida en el blog: Permite navegar por el código, copiar fragmentos y reconocer las fronteras entre capas sin instalar el proyecto. No sustituye un editor ni pretende ocultar complejidad; su función es ofrecer un mapa antes de entrar en los detalles.

Una ruta desde la configuración hasta el producto

La arquitectura separa responsabilidades para que una modificación local no obligue a reescribir el sistema completo. La tabla siguiente propone un orden de lectura y, más importante aún, asocia cada capa con la pregunta que responde.

Capa Pregunta que responde Archivos principales
Entorno. ¿Qué proyecto estamos instalando y qué necesita para ejecutarse? README.md, pyproject.toml
Configuración. ¿Qué dimensiones, unidades y equipos existen en este escenario? conf/public.toml, config.py
Contratos. ¿Qué combinaciones de valores son admisibles antes de simular? contracts.py
Datos. ¿Cómo se seleccionan, ordenan y derivan las señales de entrada? data.py
Dominio. ¿Cómo se deposita, mezcla, segrega y extrae el material? domain/kernel.py, domain/segregation.py
Reconciliación. ¿Cómo se compara una salida simulada con una referencia? domain/reconciliation.py
Orquestación. ¿Qué resultados se materializan y qué verificaciones los acompañan? defs/assets.py, definitions.py
Pruebas. ¿Qué comportamiento debe permanecer cierto después de un cambio? tests/
Producto. ¿Cómo se convierten los estados en una experiencia visual? app-src/

El archivo pyproject.toml describe el paquete de Python. Como comentamos un par de entradas atrás, TOML es un formato de configuración legible por personas, organizado mediante claves, valores y secciones, similar a un diccionario de Python. En este archivo se declaran la versión compatible de Python, las dependencias necesarias y las herramientas de desarrollo. No contiene reglas físicas; responde a una pregunta anterior y más básica: ¿Qué debe instalarse para que el código pueda ejecutarse de manera reproducible?

La configuración científica vive en conf/public.toml. Allí se expresan, como datos y no como constantes dispersas por el programa, las dimensiones de la retícula, el tamaño de celda, la densidad aparente, el ángulo de reposo, los límites granulométricos y los alimentadores. El módulo config.py carga ese documento y lo entrega a Pydantic. El fragmento siguiente es breve, pero define una frontera fundamental:

def load_spec(path: Path | None = None) -> SimulationSpec:
    """Carga la configuración pública y devuelve un contrato inmutable."""
    source = path or Path(__file__).parents[2] / "conf" / "public.toml"
    with source.open("rb") as stream:
        payload = tomllib.load(stream)
    payload["feeders"] = tuple(payload.get("feeders", ()))
    return SimulationSpec.model_validate(payload, strict=True)

La anotación Path | None indica que path puede contener una ruta o no contener valor. Si el lector no entrega una ruta, la expresión situada después de or selecciona la configuración pública. El archivo se abre en modo binario ("rb") y la función tomllib.load() transforma el TOML en un diccionario de Python. La última línea realiza la operación decisiva: model_validate(..., strict=True) exige que los datos satisfagan el contrato sin conversiones ambiguas. Un texto como "41" no se acepta silenciosamente como el entero 41.

Recordemos que los contratos se encuentran en contracts.py. Una clase como GridSpec no ejecuta el autómata; establece las condiciones mínimas para que tenga sentido ejecutarlo. Los objetos son inmutables, rechazan campos desconocidos y validan tanto valores individuales como relaciones entre ellos:

class GridSpec(ImmutableContract):
    n_east: int = Field(ge=9, le=301)
    n_north: int = Field(ge=9, le=301)
    n_vertical: int = Field(ge=4, le=200)
    cell_size_m: float = Field(gt=0.05, le=20.0)

    @model_validator(mode="after")
    def require_odd_horizontal_axes(self) -> Self:
        if self.n_east % 2 == 0 or self.n_north % 2 == 0:
            raise ValueError(
                "los ejes horizontales deben tener un numero impar de celdas"
            )
        return self

Field(ge=9, le=301) restringe un campo al intervalo comprendido entre 9 y 301, incluidos ambos extremos. En Python, el símbolo % calcula el residuo de una división; un residuo igual a cero al dividir por dos identifica un número par. El decorador @model_validator, una instrucción que modifica el comportamiento de la función escrita inmediatamente debajo, solicita una validación posterior a la creación del objeto. De esta manera, la paridad de ambos ejes deja de ser una suposición escondida en el núcleo y se convierte en una regla ejecutable con un mensaje comprensible.

Superada esa frontera, data.py se ocupa de la tabla minuto a minuto. Recordemos que un archivo parquet es un formato binario columnar: Guarda juntas las observaciones de una misma variable y permite leer sólo las columnas o filas necesarias. Polars trabaja naturalmente con este formato. La función public_minute_series() selecciona una ventana temporal y curate_minute_series() aplica el contrato tabular, conforme un encadenamiento de métodos que agiliza la lectura del código:

return (
    raw.lazy()
    .sort("timestamp")
    .with_columns(
        pl.col("feed_tph").clip(0, 10_000),
        pl.col("discharge_a_tph").clip(0, 10_000),
        pl.col("discharge_b_tph").clip(0, 10_000),
        (
            pl.col("feed_tph")
            - pl.col("discharge_a_tph")
            - pl.col("discharge_b_tph")
        )
        .truediv(60.0)
        .alias("inventory_delta_t"),
    )
    .filter(pl.col("feed_p80_in").is_between(0.05, 30.0))
    .collect()
)

El método lazy() inicia un plan de consulta sin ejecutar todavía cada operación. Las expresiones pl.col(...) describen columnas; clip() limita valores a un intervalo y alias() asigna nombre a una variable derivada. Sólo collect() solicita el resultado materializado. Esta separación permite que Polars analice el conjunto de transformaciones y optimice su ejecución, en vez de recibir una sucesión de instrucciones aisladas.

Recién después llegamos al núcleo científico del proyecto. En domain/kernel.py, una dataclass denominada StockpileState reúne dos arreglos tridimensionales de NumPy. El primero conserva la fracción de llenado de cada celda y el segundo su tamaño característico. Una dataclass es una clase de Python orientada a almacenar datos relacionados sin repetir el código habitual de inicialización. Numpy, por su parte, proporciona la posibilidad de manejar arreglos numéricos multidimensionales y operaciones eficientes sobre ellos.

Las funciones add_to_top(), remove_from_top() y remove_from_bottom() representan mecanismos físicamente distintos. Alimentar una columna ocupa primero su capacidad disponible; una avalancha retira material superficial; un feeder extrae desde la base y obliga al vacío a migrar hacia arriba. La función run_step() no esconde esa secuencia. El fragmento abreviado permite leer el orden de los eventos aun sin conocer todos los detalles de cada función:

def run_step(
    state: StockpileState,
    spec: SimulationSpec,
    feed_volume_cells: float,
    feed_p80_in: float,
    discharge_volume_cells: tuple[float, ...],
    rng: np.random.Generator,
) -> tuple[float, ...]:
    for (dn, de), weight in zip(feed_footprint, weights, strict=True):
        add_to_top(
            state,
            centre_north + dn,
            centre_east + de,
            feed_volume_cells * float(weight),
            feed_p80_in,
        )

    for feeder, volume in zip(spec.feeders, discharge_volume_cells, strict=True):
        _, size = remove_from_bottom(state, feeder.north, feeder.east, volume)
        discharged_sizes.append(size)

    for _ in range(2):
        equilibrate_surface(state, spec, rng)

    return tuple(discharged_sizes)

El objeto rng es un generador de números pseudoaleatorios. La función nativa zip(..., strict=True) empareja elementos de dos colecciones y levanta un error si sus longitudes son diferentes. Este detalle evita, por ejemplo, que un caudal quede sin un feeder por una discrepancia silenciosa entre configuración y datos.

La capa de Dagster aparece sólo cuando las reglas científicas ya existen. Recordemos que un activo de datos es un resultado persistente con identidad propia, como una tabla curada o una repetición del stockpile. El decorador @dg.asset registra una función como productora de ese resultado. Un chequeo de activos es una verificación asociada al activo; puede detener el flujo cuando una condición indispensable deja de cumplirse o publicar una métrica para evaluación posterior.

@dg.asset(group_name="engineering", kinds={"python", "polars"})
def public_minute_curated(public_minute_raw: pl.DataFrame) -> pl.DataFrame:
    return curate_minute_series(public_minute_raw)


@dg.asset_check(asset=public_minute_curated, blocking=True)
def minute_contract(
    public_minute_curated: pl.DataFrame,
) -> dg.AssetCheckResult:
    checks = [
        public_minute_curated["timestamp"].is_sorted(),
        public_minute_curated.null_count().row(0)
        == (0,) * public_minute_curated.width,
        public_minute_curated["feed_p80_in"].is_between(0.05, 30.0).all(),
    ]
    return dg.AssetCheckResult(passed=all(checks))

La dependencia entre activos surge de la firma de la función: public_minute_curated() recibe public_minute_raw, por lo que Dagster puede inferir la flecha entre ambos. El módulo definitions.py reúne los activos y checks en un objeto Definitions, que funciona como punto de entrada para las herramientas de Dagster. La orquestación no reimplementa el cálculo tabular ni el autómata, sino que los invoca y registra sus resultados.

El último tramo pertenece al producto. La carpeta app-src/ contiene la aplicación escrita en TypeScript. React coordina el instante activo y Canvas dibuja los estados exportados, tal como vimos en el capítulo anterior. Esta capa consume un contrato; no vuelve a decidir cómo cae o se extrae el mineral. La frontera impide que una regla de visualización termine convertida accidentalmente en una segunda versión de la física del proceso que hemos modelado.

Seguir una señal y comprobar sus invariantes

Una vez reconocidas las capas, podemos seguir una variable concreta. La variable feed_tph representa el flujo másico de alimentación en toneladas por hora. Su recorrido comienza como una columna de la tabla pública y termina como una modificación espacial del estado:

  1. La función public_minute_series() selecciona el período solicitado desde el archivo parquet.
  2. La función curate_minute_series() ordena la serie, acota rangos y calcula variables derivadas mediante Polars.
  3. El activo stockpile_replay resume la información en intervalos de quince minutos.
  4. El flujo másico se multiplica por la duración del intervalo para obtener toneladas.
  5. Las toneladas se dividen por la masa que representa una celda para obtener volumen discretizado.
  6. La función run_step() distribuye ese volumen sobre la huella de alimentación.
  7. La función add_to_top() actualiza llenado y granulometría sin superar la capacidad de la columna.
  8. La suma vertical de llenados produce la superficie y, a partir de ella, la altura simulada.
  9. El activo publica la serie y el visor la presenta junto con la referencia disponible.

Esta lectura conserva la causalidad del proceso subyacente. Si la altura cambia de manera inesperada, podemos preguntar en qué transformación apareció la diferencia: En el flujo másico curado, en la conversión temporal, en la masa por celda, en la deposición o en la extracción. Mirar directamente el gráfico final no permite distinguir esas posibilidades.

La propiedad feed_p80_in sigue una ruta paralela, pero no idéntica. \(P_{80}\) es el tamaño por debajo del cual pasa el 80 % del material. Al depositarse un volumen nuevo, _mix() calcula un promedio ponderado entre la propiedad existente y la entrante. Durante la relajación superficial, segregate_sizes() produce componentes fino y grueso cuya combinación conserva el tamaño característico original. En la descarga, el tamaño retirado se pondera por el volumen extraído desde cada celda y luego se agrega por línea.

Seguir esta propiedad revela también una limitación del modelo: En ningún punto se genera una distribución granulométrica completa por celda. El estado conserva un tamaño característico. Por eso el visor puede comparar el \(P_{80}\) simulado con curvas medidas, pero no debe dibujar una distribución simulada que el núcleo científico del proyecto nunca produjo. Leer el código no sirve únicamente para encontrar errores; también delimita qué afirmaciones puede sostener el producto.

Las invariantes son propiedades que deben permanecer ciertas aunque el estado cambie. La conservación de volumen es una de ellas. Una prueba pequeña deposita 2.4 celdas equivalentes, extrae 0.7 y verifica que la diferencia en el inventario sea exactamente igual al volumen retirado:

def test_feed_and_discharge_conserve_volume() -> None:
    spec = load_spec()
    state = StockpileState.empty(spec)
    north = spec.grid.n_north // 2
    east = spec.grid.n_east // 2

    add_to_top(state, north, east, 2.4, 4.2)
    before = state.fill.sum()
    removed, size = remove_from_bottom(state, north, east, 0.7)

    assert np.isclose(before - state.fill.sum(), removed)
    assert np.isclose(removed, 0.7)
    assert np.isclose(size, 4.2)

El statement assert declara una condición que debe cumplirse; si resulta falsa, la prueba falla. La función np.isclose() compara números de punto flotante con una tolerancia pequeña, porque muchas operaciones decimales no pueden representarse de manera exacta en un computador. La prueba no necesita reproducir 61 días para proteger la conservación. Aísla el mecanismo mínimo y entrega un diagnóstico mucho más claro.

Si el inventario de una ejecución completa no cerrara, seguiríamos esa misma filosofía. Primero crearíamos una grilla pequeña y vacía; después añadiríamos un volumen conocido, retiraríamos una fracción y compararíamos las sumas. Sólo al aprobar esas operaciones activaríamos segregación, relajación superficial y agregación temporal. Depurar dos semanas desde el comienzo mezcla demasiados mecanismos y permite que errores opuestos se compensen entre sí.

Verificar y extender sin romper las fronteras

El repositorio incluye herramientas para responder cuatro preguntas diferentes. El módulo uv instala dependencias y ejecuta comandos dentro de un entorno controlado. Ruff es una herramienta del ecosistema Python que detecta errores estáticos y mantiene convenciones de estilo. Pytest descubre y ejecuta las funciones de prueba. La interfaz de línea de comandos de Dagster materializa los activos, mientras npm instala las dependencias de la aplicación web y solicita su compilación.

Con esas definiciones, la secuencia de verificación deja de ser una colección críptica de órdenes:

uv sync --group dev
uv run ruff check .
uv run pytest

export DAGSTER_HOME="$PWD/.dagster_home"
uv run dagster asset materialize --select '*' -m stockpile_ca.definitions

cd app-src
npm install
npm run build

La primera instrucción crea o actualiza el entorno con las dependencias de desarrollo. La segunda inspecciona el código sin ejecutar la simulación. La tercera corre las pruebas. DAGSTER_HOME es una variable de entorno —un valor que el sistema operativo entrega a los programas— que indica dónde Dagster debe guardar su estado local. El comando asset materialize ejecuta los productores necesarios para construir todos los activos seleccionados. Finalmente, las órdenes de npm verifican TypeScript y generan el producto web publicable.

Las pruebas cubren niveles diferentes. El módulo test_contracts.py verifica configuraciones válidas e inválidas; test_data.py comprueba determinismo, completitud y presencia de fenómenos operacionales; test_domain.py protege conservación, orden de extracción y segregación; test_dagster_graph.py fija el linaje esperado; y test_anonymisation.py revisa que el producto público conserve nomenclatura genérica y no incorpore identificadores restringidos. Una compilación exitosa no reemplaza estas pruebas: Sólo demuestra que el programa pudo construirse, no que representa correctamente el dominio.

Las fronteras también orientan futuras extensiones. Para incorporar edad de material, añadiríamos al estado un arreglo que conserve el momento de edad, definiríamos reglas de mezcla y transferencia, y escribiríamos pruebas de conservación antes de exponer la variable en el visor. Dagster no tendría que cambiar hasta que decidiéramos publicar esa salida como parte de un activo de datos.

Si cambiara la fuente de datos, el dominio tampoco debería reescribirse. Sustituiríamos el activo de entrada y conservaríamos el contrato tabular curado. Si agregáramos particiones diarias, modificaríamos la definición operacional de los activos sin insertar calendarios dentro del núcleo. Esta separación no elimina el trabajo, pero evita que una decisión de infraestructura se propague hacia la física.

Cuando la documentación también se deriva del código

El explorador incluye el script build_dagster_snapshot.py. Un script no es más que un programa pequeño orientado a una tarea concreta. En este caso, tal script no mantiene manualmente una segunda lista de activos: Importa defs, solicita a Dagster el grafo resuelto y exporta sus nodos, grupos, checks y dependencias. Si añadimos una flecha al sistema y regeneramos la vista, la documentación cambia con la arquitectura.

El mismo principio gobierna el script build_source_explorer.py. La navegación que encabeza este capítulo se genera desde los archivos reales y un orden editorial declarado. No copiamos fragmentos a una página independiente que pueda quedar obsoleta silenciosamente. El código continúa siendo la fuente de verdad, mientras la interfaz agrega contexto para leerlo.

La edición pública es deliberadamente más pequeña que un sistema conectado a una operación. No contiene credenciales, conectores privados ni servicios en línea. Sí contiene lo necesario para reproducir el razonamiento: Configuración, contratos, transformación tabular, estado tridimensional, reglas de dominio, activos, checks, pruebas y aplicación visual. Esa reducción no convierte el repositorio en un juguete; hace visibles sus decisiones esenciales.

Este recorrido final muestra una idea que atraviesa todo el proyecto. Pydantic protege el mundo posible, Polars organiza las señales, Numpy representa el estado, Dagster publica el linaje de datos y React coordina la experiencia visual. Ninguna herramienta reemplaza el modelo físico ni la responsabilidad de validarlo. El valor de la arquitectura consiste en que cada decisión pueda encontrarse, explicarse, probarse y modificarse sin perder de vista el fenómeno que representa.
