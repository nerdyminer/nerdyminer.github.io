Un modelo de forecasting Bayesiano jerárquico para explicar el tratamiento de molienda

De archivos estáticos a una explicación contextual del rendimiento con Kedro y PyMC

Este proyecto es un ejemplo de cómo un modelo Bayesiano jerárquico puede ser usado para explicar el rendimiento de una planta de molienda en función del contexto operacional. A través de un flujo reproducible que integra datos sintéticos, ingeniería de datos, ciencia de datos y modelamiento Bayesiano, se construye un sistema que permite descomponer el rendimiento observado en componentes explicables por el contexto y un residuo no explicado.

NoteUn caso ficticio, construido para aprender

Todos los datos del proyecto fueron generados desde cero para este blog. Las fechas futuras, las coordenadas cartesianas locales, las capacidades, los identificadores y la configuración del circuito son supuestos didácticos: no representan ni fueron derivados de una operación minera real. Esta separación es importante porque nos permite conservar relaciones industriales plausibles sin publicar la huella de una faena.

Nuestro objetivo es responder a la pregunta: ¿Cuánto del rendimiento observado era esperable por el contexto que recibió la planta y cuánto queda sin explicar por ese contexto?. La respuesta se presenta en forma de un gráfico de cascada auditable, que permite visualizar las contribuciones de diferentes variables contextuales al rendimiento esperado. Tales variables incluyen geología, procedencias de mineral, granulometría, estado de sistemas periféricos de la molienda y dureza in-situ del mineral.

La planta concentradora

La planta concentradora es un sistema complejo que recibe mineral de diferentes procedencias y con distintas características físicas y químicas. La eficiencia del proceso de molienda depende de múltiples factores, incluyendo la dureza del mineral, la distribución granulométrica, la disponibilidad de los equipos y las condiciones operacionales.

Nos enfocaremos en la molienda SAG y en sus interacciones con diversos sistemas periféricos que ocurren antes, durante y después de la molienda misma, tales como la alimentación primaria, el procesamiento del material recirculado, la molienda secundaria y la clasificación por medio de hidrociclones. Para conservar la riqueza del problema sin imitar una faena, supondremos un circuito didáctico de dos líneas que recibe mineral desde ocho fuentes ficticias, etiquetadas de SOURCE_A a SOURCE_H. Cada fuente posee una mezcla geológica y una dureza distintas, construidas por el generador del proyecto para que el contexto cambie a través del tiempo.

El producto final

El modelo Bayesiano de tratamiento tiene por objetivo desacoplar el rendimiento observado en componentes explicables por el contexto y un residuo no explicado. La salida del modelo es un gráfico de cascada que muestra cómo cada variable contextual contribuye al rendimiento esperado, permitiendo a los operadores y analistas entender mejor las causas detrás de las variaciones en el rendimiento.

En todo el período ficticio fuera de muestra, el tratamiento contextual medio fue de aproximadamente 2232 tph, prácticamente igual al tratamiento sintético observado. La diferencia entre ambos es el residuo operacional agregado, cercano a cero en esta ejecución de prueba. No conviene leer esta coincidencia como una propiedad de una planta: es una comprobación del generador y de la identidad contable del bridge. La consistencia entre el residuo agregado y el sesgo neto reportado en validación sigue siendo una prueba útil de que la reportería no alteró el universo, la agregación o el signo del tratamiento.

Arquitectura, framework y ejecución

El proyecto está construido sobre Kedro, un framework de ingeniería y ciencia de datos que permite estructurar proyectos de manera modular y reproducible. La arquitectura del proyecto sigue un enfoque de pipelines, donde cada etapa del flujo de trabajo se encapsula en una pipeline independiente, con entradas, salidas y parámetros claramente definidos.

Suponiendo que el proyecto ya ha sido clonado y que se han instalado las dependencias en una carpeta denominada proyectos/bayesian-tph-forecasting, la ejecución del flujo completo se puede realizar con los siguientes comandos:

cd proyectos/bayesian-tph-forecasting
uv sync --extra dev
uv run kedro run
uv run kedro viz run

Después del acceso al proyecto mismo, las instrucciones anteriores realizan las siguientes acciones:

  • uv sync --extra dev instala las dependencias de desarrollo y sincroniza el entorno virtual.
  • uv run kedro run ejecuta todas las pipelines del proyecto, generando los artefactos intermedios y finales según lo definido en el catálogo de datos.
  • uv run kedro viz run inicia kedro-viz, una herramienta de visualización del DAG (grafo dirigido acíclico) de las pipelines, permitiendo inspeccionar la estructura y las dependencias del flujo de trabajo.

Las pipelines del proyecto se registran en el archivo pipeline_registry.py, donde se definen las entradas, salidas y parámetros de cada pipeline. Los datos utilizados en el proyecto están declarados en el catálogo de datos, descrito por el archivo catalog.yml, mientras que los parámetros ajustables se encuentran enel diccionario parameters.yml. Estas piezas son típicas en un proyecto de Kedro y permiten una gestión clara de los datos y la configuración del proyecto.

DAG global del proyecto

En términos de flujo de datos, el proyecto puede representarse como un DAG global que muestra cómo las diferentes pipelines se conectan entre sí. Cada pipeline representa una etapa del proceso, desde la extracción de datos hasta la generación de reportes y la aplicación final.

El registro global suma las cuatro pipelines. Cada una conserva su namespace, sus entradas y salidas públicas y sus parámetros explícitos. Esa composición —no un notebook que depende de su estado de ejecución— es la unidad reproducible del proyecto.
